## 1. 현재 경로(v1.1.2)의 구조와 한계

### 1.1 지금 경로가 만들어지는 방식 (`js/dross.js`)
| 요소 | 현재 방식 | 결과 |
|---|---|---|
| 툴 자세 | `levelPose(p, dir)`: 툴 Z = 수직 아래, 툴 X = 스윕 방향. 한 사이클 동안 방향이 바뀌지 않음 | **스쿱이 늘 수평이고, 방향(yaw)이 레인 방향으로 고정** → J6가 거의 돌지 않음 |
| 레인 | `skimLanes`: 스나우트 쪽(X 2070) → 앞벽 쪽(X 1330)으로 당기는 **X축 평행 직선**, Y 6개(±670) | 모든 스윕이 같은 방향의 평행선 |
| 레인 선택 | `chooseLane`: 드로스 수가 가장 많은 레인(탐욕, 1단계 앞만 봄) | 순서 최적화 없음 |
| 여유 | 장애물 여유 20 + 30 mm를 지키며 사각 스쿱(360 × 360) 전체가 벽·스나우트에서 떨어져야 함 | **벽 앞 띠·모서리가 비어 남음** |
| 덤프 | 박스 위 8방향 중 처음 통과하는 방향, 105° 기울임 | 덤프에서만 J6·손목이 크게 움직임 |

### 1.2 남는 드로스 (REVIEW_v1.1.1 n-3)
- 스나우트 앞 약 50 mm, 포트 앞벽 앞 약 160 mm, 좌·우 벽 앞 약 180 mm 띠의 드로스는 레인이 닿지 않아 남는다.
- 네 모서리는 두 띠가 겹쳐 더 많이 남는다. 실제 현장 영상에서도 벽 쪽에 드로스가 쌓인다.
- 운반·덤프 중 흘림이 사이클당 0~1개 있다(n-2). 측면 로봇의 작은 스쿱은 더 많다(n-8).

### 1.3 J6와 툴 방향이 실제로 바꿀 수 있는 것 (설계 근거)
- 6축 로봇에서 TCP **위치 3 + 방향 3 = 6**이 정해지면 관절 6개도 정해진다(IK 해 가지 선택은 제외). 따라서 "각 관절의 최적 각도"를 찾는 것은 결국 **툴 경로(위치)와 툴 방향(yaw·pitch·roll)을 시간에 따라 어떻게 바꿀지**를 찾는 문제다.
- 스쿱이 수평이고 툴 축이 수직이면 **J6 회전 = 스쿱 yaw(진행 방향 대비 스쿱 방향) 회전**이다. 사용자가 짚은 그대로다.
- **주의할 점(가설로 둔다):** 정사각 스쿱은 yaw만 돌려서는 벽에 더 가까이 붙지 못한다. 45° 돌리면 대각선이 길어져 오히려 더 떨어진다. 벽 앞 드로스를 떠내는 효과는 아래에서 나올 것으로 본다.
  1. **스윕 방향을 바꿈:** 벽과 나란히, 또는 벽에서 바깥으로 긁어 내는 스트로크
  2. **스윕 중 yaw를 돌림(회전 스윕):** 스쿱 가장자리가 그리는 궤적이 넓어지고, 회전이 만드는 흐름이 벽 띠의 드로스를 끌어냄
  3. **기울임(pitch/roll):** 벽 쪽 가장자리를 낮추고 반대쪽을 들면 스쿱 끝이 벽 띠에 들어감. 여유거리는 지키고, 캡슐 모델 기준으로 검사
  4. **모서리 대각선 스트로크:** 모서리를 향해 45°로 들어가 끌어냄
  5. **스트로크 순서:** 벽 띠 드로스를 먼저 중앙으로 끌어낸 뒤 일반 레인으로 떠냄
- 이 가설은 0단계(실현성 확인)에서 사람이 만든 변형 몇 가지로 먼저 확인한다. 효과가 없으면 툴 형상 변경 같은 다른 자유도를 검토한다(11장).

## 2. 목표 / 비목표

### 2.1 목표
1. **스트로크 표현 확장:** 직선 + 고정 yaw만 쓰던 스윕을 **곡선 경로 + 시간에 따라 바뀌는 yaw·기울임 + 잠김 깊이·속도**로 표현하고, 기존 안전 게이트를 통과하게 실행한다.
2. **AI가 스트로크를 고른다:** 사람이 레인을 정하지 않는다. 지금의 드로스 분포를 보고 AI가 다음 스트로크(어디서, 어느 방향으로, 스쿱을 어떻게 돌리며)를 정한다.
   - 단계적으로: 최적화(L1) → 학습 정책(L2), 4장
3. **벽 띠·모서리 드로스까지 회수:** 규칙 기반(v1.1.2) 대비 잔여 드로스와 사이클 수를 줄인다(성공 기준 8장).
4. **앱에서 비교:** 규칙 경로와 AI 경로를 같은 드로스 배치에서 나란히 비교하고, J6·툴 방향 변화를 그래프로 보여 준다(v1.1.2 계측 재사용).

### 2.2 연구 질문
| RQ | 질문 |
|---|---|
| RQ1 | 툴 방향(J6 yaw·기울임) 자유도를 쓰면 규칙 경로가 못 떠낸 벽 띠·모서리 드로스를 얼마나 회수하는가? |
| RQ2 | 드로스 분포를 보고 스트로크를 고르는 학습 정책이 처음 보는 분포에서도 최적화(L1) 결과에 가까운 성능을 내는가(일반화)? |
| RQ3 | 회수량·사이클 시간·흘림·에너지(추정 전류)의 균형점은 어디인가(다목적)? |

### 2.3 비목표 (v3.0.0에서 하지 않음)
- 관절 토크·전류를 직접 출력하는 저수준 제어 학습 — AI는 **스트로크(경로·방향 파라미터)** 를 정하고, 관절값은 기존 IK·직선 보간·경로 계획이 만든다.
- 안전 게이트 우회 — AI 경로도 적용 전 안전 검사를 반드시 통과한다.
- 브라우저 안에서 학습 — 학습은 오프라인(Python). 앱은 학습 결과(가중치 JSON)로 **추론만** 한다.
- 새 런타임 의존성 — 브라우저는 Three·Rapier 두 개만 쓴다. 정책 추론은 작은 신경망을 순수 JS로 계산한다(ONNX Runtime 등 추가 안 함).
- 실제 로봇 적용 — 시뮬레이터 안에서 검증한다.

## 3. 핵심 설계 — 계층 구조

```
 [관측] 드로스 점유 격자(욕면 위) + 로봇 상태 + 남은 시간
        │
        ▼
 [AI 정책 / 최적화기]  ──  "다음 스트로크 파라미터" a
        │                   (시작점, 끝점, 곡률, yaw 시작·끝, 기울임, 잠김 깊이, 속도)
        ▼
 [스트로크 실행기 planStroke]  ← 기존 v1.1.2 자산 재사용
   접근(reach: 직선 → 높이 경유 → RRT) → 하강 → 스윕(곡선 + 방향 보간) → 상승 → 운반 → 덤프(기존)
   모든 구간: IK(이전 해 시드) + 세분 안전 검사(sweepCheck) — 실패하면 '불가' 반환
        │
        ▼
 [물리 시뮬레이션] Rapier: 드로스 입자·부력·스쿱 접촉 → 회수·흘림·잔여 지도
        │
        ▼
 [보상] 회수(kg) + 벽 띠 가중 − 시간 − 흘림 − 불가/차단 − J6 과회전 …
```

- **AI가 정하는 것:** 스트로크 파라미터(아래 3.1)와 스트로크 순서.
- **기존 코드가 보장하는 것:** 관절값 계산(IK), 관절 한계·충돌·특이점 회피, 실행 궤적 시간 파라미터화, 덤프 동작.
- 이 구조라서 AI가 이상한 값을 내도 로봇은 안전하다. 불가능한 스트로크는 실행 전에 걸러지고 보상에서 벌점을 받는다.

### 3.1 스트로크 파라미터 (행동 공간, 초안)
| 파라미터 | 뜻 | 범위 (초안) |
|---|---|---|
| `p0 = (x0, y0)` | 스윕 시작점(욕면 위, 스쿱 중심) | 포트 안쪽(벽 여유 포함) |
| `p1 = (x1, y1)` | 스윕 끝점 | 포트 안쪽 |
| `bend` | 경로 곡률(2차 베지어 제어점의 옆 방향 오프셋) | −400 ~ 400 mm |
| `yaw0`, `yaw1` | 스윕 시작·끝의 스쿱 방향(진행 방향 대비). 둘 사이는 부드럽게 보간 → J6 회전 | −90° ~ 90° |
| `pitch`, `roll` | 스윕 중 기울임(앞뒤·좌우) | −15° ~ 15° (11장에서 확정) |
| `depth` | 잠김 깊이 | 20 ~ 75 mm (현재 설정 범위) |
| `speed` | 스윕 속도 | 30 ~ 250 mm/s (현재 설정 범위) |
| (선택) `retreat` | 끝에서 스쿱을 비틀어 담기(마지막 yaw 회전량) | 0 ~ 45° |

- 운반·덤프 구간은 v1.1.2와 같다(뒤로 12° 기울임, 8방향 덤프). 다만 스윕 끝 yaw가 바뀌므로 운반 시작 자세가 달라진다.
- **J6 누적 회전 제한:** 실제 스키머에는 호스·케이블이 있어 J6를 계속 같은 방향으로 돌릴 수 없다. 사이클 시작 대비 ±270°(초안, 11장)를 넘지 않게 하고, 넘으면 다음 접근에서 되감는다.

### 3.2 관측 (상태 공간, 초안)
- **드로스 점유 격자:** 포트 안쪽(2,600 × 1,800 mm)을 50 mm 칸 52 × 36 격자로 나눈다(초안). 칸마다 드로스 질량(kg)을 넣는다. 정책 입력용으로는 13 × 9 등으로 줄일 수 있다.
- **구역 요약:** 벽 띠(앞·좌·우·스나우트 앞)와 모서리 4곳의 잔량.
- **로봇 상태:** 현재 관절값, J6 누적 회전, 툴 위치.
- **작업 상태:** 남은 시간(또는 남은 사이클 수), 측면 로봇 구역(있으면 막힌 영역).

## 4. AI 방식 — 단계적으로 (추천)

| 단계 | 방식 | 하는 일 | 장점 | 한계 |
|---|---|---|---|---|
| **L0** | 규칙 베이스라인 + 사람이 만든 변형 | v1.1.2 레인(기준) + 벽면 스윕·회전 스윕·모서리 대각선 몇 가지를 손으로 정의 | 가설(1.3) 검증, 비교 기준 | 경우의 수를 다 못 봄 |
| **L1** | 블랙박스 최적화 (CMA-ES, 베이지안 최적화) | **주어진 드로스 배치 하나**에 대해 3.1 파라미터를 시뮬레이션으로 반복 평가해 최적 스트로크(또는 스트로크 3~5개 묶음)를 찾음 | 학습 데이터 없이 바로 "최적에 가까운 답". 결과 = 정답 예시 | 배치마다 수백 번 시뮬레이션 → 실시간 사용 불가 |
| **L2** | 학습 정책 (모방 학습 → 강화학습 미세 조정) | L1이 찾은 (분포 → 좋은 스트로크) 쌍으로 정책을 먼저 가르치고(모방), PPO 등으로 다듬음 | **처음 보는 분포에서도 한 번에 스트로크를 정함** → 앱에서 실시간 사용 | 학습 시간, 일반화 검증 필요 |
| L3 (선택) | 스트로크 내부 미세 최적화 | 정해진 스트로크 안의 관절 궤적을 CHOMP 스타일 최적화(`optimizer.js`)에 회수량·흘림 대리 비용을 더해 다듬음 | 흘림·시간 추가 개선 | 대리 비용 설계 필요 |

- **추천 경로:** L0 → L1 → L2. L1이 "학습 없이도 이만큼 좋아진다"를 먼저 보여 주고, L2는 그 결과를 실시간으로 쓰게 만든다.
- **정책 구조(초안):** 작은 CNN(격자) + MLP(로봇 상태)를 거쳐 스트로크 파라미터의 평균·분산을 낸다. 가중치 수만 개 수준으로 순수 JS 추론이 1 ms 안에 끝나게 한다.
- **학습 환경:** Python(PyTorch, CMA-ES 라이브러리) ↔ Node 헤드리스 시뮬레이터(JSON 줄 단위 표준 입출력). 병렬 작업자 여러 개를 쓴다(5장).

## 5. 학습·평가용 시뮬레이션 환경

### 5.1 환경 API (Node, DOM 비의존 `js/skim-env.js`)
```
reset({ seed, drossCount, distribution, robotId, sides }) → obs
step(action) → { obs, reward, done, info: { collected, spilled, wallBandCollected, cycleS, feasible, blockedStage, j6TurnDeg, energyJ } }
```
- `distribution`: 고르게 / 벽 쏠림 / 모서리 쏠림 / 스나우트 앞 쏠림 / 무작위 덩어리
- 한 `step` = 스트로크 1개(접근 → 스윕 → 운반 → 덤프 → 복귀). 물리로 결과를 낸다.
- 한 에피소드 = 고정 시간(예: 120 s) 또는 스트로크 N개.
- **불가능 스트로크:** 계획 단계에서 실패하면 시뮬레이션 없이 바로 `feasible = false`와 벌점을 돌려준다(빠름).
- **재현성:** 같은 seed + 같은 행동 열이면 같은 결과가 나온다. 시간 제한 후처리는 반복 횟수 고정 모드를 쓴다.

### 5.2 Python 다리 (`train/`)
- `train/env.py`: Node 프로세스를 띄워 JSON 줄로 `reset`·`step`을 주고받는 gymnasium 호환 환경.
- `train/optimize_cma.py`(L1), `train/imitate.py` + `train/rl_ppo.py`(L2), `train/export_policy.py`(가중치 → `policy.json`).
- 가상환경은 `train/.venv`(git 제외)에 만든다. 전역 설치는 하지 않는다.

### 5.3 속도와 대리 모델
- v1.1.2 측정에서 물리 60 s는 약 2.5 s(Node)였다. 스트로크 1개(약 25~30 s 시뮬레이션)는 계획 포함 약 1.5~3 s로 예상한다(1단계에서 측정).
- L1(배치 1개당 수백 평가)은 작업자 8개로 배치당 수 분이 걸린다.
- L2 강화학습에 수십만 스텝이 필요하면 물리만으로는 느리다. 그래서 **2D 대리 모델**(스쿱이 쓸고 지나간 면적·방향으로 입자를 옮기는 빠른 근사)로 먼저 학습하고, 물리 환경에서 미세 조정·평가한다. 대리 모델의 정확도는 물리와 비교해 보고한다.

### 5.4 보상 (초안, 가중치는 실험으로 조정)
```
r = w1·회수 kg + w2·벽 띠·모서리 회수 kg − w3·스트로크 시간 s − w4·흘림 개수
    − w5·[불가능 / 게이트 차단] − w6·max(0, |J6 누적| − 한계) − w7·추정 에너지 J (선택)
```

### FR-54 방향이 있는 스쿱 자세와 곡선 스윕 (P1)
- `orientedPose(p, heading, { yaw, pitch, roll })`: `levelPose`를 일반화한다. 툴 X를 진행 방향에서 yaw만큼 돌리고 pitch·roll로 기울인다.
- `planStroke(input, stroke)`: `planSkimCycle`을 일반화한다.
  - 스윕 = 2차 베지어 곡선(`p0 → 제어점 → p1`)을 일정 간격 TCP 목표로 나눔
  - 각 점의 yaw·pitch·roll은 시작 → 끝으로 부드럽게 보간
  - `linearMove`를 이어 붙이고(IK는 이전 해를 시드로), 구간마다 세분 안전 검사
  - 기존 직선 레인은 `bend = 0, yaw0 = yaw1 = 0, pitch = roll = 0`인 특수 경우 → **v1.1.2와 같은 결과**(회귀)
- 실패하면 `{ ok: false, stage, message }`(어느 구간에서 왜)를 돌려준다.

## 7. 안전·호환 원칙
- AI 경로를 포함한 모든 로봇 이동은 **적용 전 안전 검사(세분 sweep)** 를 통과해야 한다. 정책 출력은 범위를 잘라 쓰고, 불가능하면 실행하지 않는다(알람 대신 '불가' 표시 후 규칙 경로로 대체할지 선택).
- 고정 모드·셀 꺼짐·경로 방식 '규칙'은 v1.1.2와 같게 동작한다. 기존 Node 테스트 13종은 계속 통과해야 한다.
- 저장 스키마(localStorage): 경로 방식·정책 저장을 넣으면 `state.js` sanitize·migrate와 이 PRD 스키마 절을 함께 고친다(11장 결정 후).
- 회수·흘림 수치는 시뮬레이터(구형 입자, 근사 부력·마찰) 기준이다. 실제 드로스(점착·덩어리)와 다르다고 보고서에 밝힌다.

## 12. v2.0.0과의 관계
- v2.0.0(이상·고장 데이터, 조건부 threshold)과 v3.0.0(AI 경로 최적화)은 둘 다 v1.1.2를 뼈대로 **독립 개발**한다. 둘 다 `cell-sim`류 헤드리스 실행기가 필요하다.
  - 먼저 만든 쪽의 실행기 설계를 다른 쪽이 그대로 가져온다. 이름과 API를 맞춘다: `runEpisode` / `skim-env`.
- 나중에 합칠 수 있는 지점
  - v2의 이상 판정(근접·흘림)을 v3 보상의 벌점으로 쓰기
  - v2의 조건부 전류 경계를 v3 정책의 제약으로 쓰기(전류가 경계를 넘는 스트로크 회피)
- 두 버전을 합칠 때는 새 버전 폴더에서 한다. 릴리스한 폴더는 수정하지 않는다.
